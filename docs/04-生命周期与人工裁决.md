# 04 · 生命周期与人工裁决

这是整套系统最有意思的一部分，也是花时间最多的一部分。

前面两篇解决的是「进出有规矩」。但规矩管不了一件事：**一条当初完全合格的记忆，几个月后变得不该再用了**。运行态事实过期了、方案被推翻了、两条记忆开始互相打架、某条记忆的主体归属其实是错的。

这些判断机器做不了，必须人来做。问题是怎么让人做得动。

---

## 全链路

```
周期性审计（只读扫全库）
   ↓  产出：候选队列 JSON —— 无正文，但 metadata 仍需保护
本地审核前端 / CLI
   ↓  status  查看积压
   ↓  list    列出候选（ID + 哈希前缀 + 当前结论，仍然无正文）
   ↓  reveal  按需单条揭示正文（审核程序不主动持久化正文）
   ↓  preview 预览这批修改的影响，得到一个批次摘要值
   ↓  apply   回传相同摘要值才允许执行
裁决台账 SQLite
   ↓  批次头 + 批次明细 + 追加式事件流 + 生命周期覆盖层
自动召回
   ↓  逐条叠加覆盖层，只有「有效 + 保持有效」才进 AI 上下文
```

---

## 第一步：审计产出不含正文的候选队列

当前实例通过周期性任务扫描全库，产出一份候选清单。精确调度频率属于实例运行配置，不在公开文档中保留。这份清单的关键特征是**它不携带记忆正文**：

```json
{
  "schema_version": 2,
  "generated_at": "<ISO8601 UTC>",
  "owner_id": "<owner-id>",
  "automatic_mutation": false,
  "automatic_retrieval_policy": "pending_candidates_excluded",
  "unique_count": 0,
  "classification_count": 0,
  "items": [
    {
      "memory_id": "<uuid>",
      "content_sha256": "<64 hex>",
      "categories": ["expiry_candidates"],
      "reason_codes": ["包含阶段性运行态事实，需要复验"],
      "related_memory_ids": [],
      "last_seen_at": "<ISO8601>"
    }
  ]
}
```

几个字段值得解释：

- `automatic_mutation: false` 是一句**声明**：生产方声称这份产物不触发自动改写。消费方可以校验该值，但真正不改写仍取决于应用代码；字段本身没有执行能力。
- `automatic_retrieval_policy: pending_candidates_excluded` 声明未裁决候选应默认退出自动召回。这是供消费方核对的策略声明；真正的「先隔离、后审议」必须由召回代码执行。
- `unique_count` 和 `classification_count` 分开，因为**一条记忆可以命中多个分类**（既过期又冲突是常见组合）。

### 五类候选

| 分类 | 含义 |
|---|---|
| `expiry_candidates` | 包含阶段性运行态事实，需要复验或标过期 |
| `conflict_candidates` | 与另一条记忆口径冲突 |
| `noise` | 长会话片段、原文型记忆，本来就不该进长期库 |
| `metadata_risk` | 涉及职业/简历/第三方资料，但缺少主体归属相关的字段 |
| `duplicate` | 精确重复 |

`metadata_risk` 这一类是实践中加出来的。触发场景：某次对话里出现了别人的简历、别人公司的资料，自动捕获逻辑把它当成「用户的事实」写了进去。这类记忆最危险的地方是**它看起来完全正常** —— 字段齐全、格式正确、内容通顺，只有主体是错的。所以判定不靠内容，靠「缺不缺归属相关的元数据」。

对应的写入侧策略是：**主体归属不清就跳过，而不是推断**。宁可少记一条，不可记错主人。

### 不含正文，不等于不敏感

三个理由，按重要性排序：

1. **这个文件不在加密卷里**。它是审计产物，可能进入普通备份或同步范围。去掉正文可以减少明文副本，但不能消除风险。
2. **ID、哈希和关系仍会泄露结构**。关联记忆 ID、出现时间和分类能够暴露活动模式；稳定哈希还可能被用于比对已知内容。
3. **自由文本理由可能带出正文信息**。生成理由时必须限制内容，使用者也应把整个队列按敏感 metadata 保护。
4. **内容哈希用于绑定版本**。`(ID, 哈希)` 这个组合定位「哪条记忆的哪个版本」，但它不是匿名化手段。

## 第二步：五个动作

审核入口提供五个动作，其中四个是只读的，只有最后一个会写库。

| 动作 | 只读 | 做什么 |
|---|---|---|
| `status` | ✓ | 汇总积压：三个产物是否健在、总数、待审数、按结论分布 |
| `list` | ✓ | 队列与覆盖层联表，输出 ID + 哈希前缀 + 当前结论 + 是否可召回 |
| `reveal` | ✓ | 单条揭示正文，直连底层库只读查询；审核程序不主动持久化正文 |
| `preview` | ✓ | 校验批次，算出摘要值，返回逐条的前后影响 |
| `apply` | ✗ | 必须回传与预览一致的摘要值，单事务写入 |

`status` 有两个固定为假的返回字段：`automatic_delete: false` 和 `supersede_supported: false`。它们让调用方看见当前接口能力声明；真正的行为仍由服务端实现决定。第二个下面单独说。

`list` 的返回里有一个 `raw_access: false` 标记 —— 明确告诉调用方「你拿到的东西里没有正文」。

`reveal` 是审核流程中查看正文的动作。它直连底层向量库做只读查询，命中之后还要再校验一次归属，不符就拒绝。当前审核程序不主动把正文写入自己的持久化文件；这不等于证明操作系统缓存、崩溃报告、截屏工具或上层界面绝不会留下副本。

## 第三步：预览摘要 —— 防陈旧提交

这是整套流程里最值得抄的一个设计。

问题场景：用户打开审核界面，勾选了二十条记忆的处理方式，点预览，看了影响，然后去泡了杯咖啡。回来点应用 —— 但这中间队列已经被定时审计更新过了，某条记忆的内容变了，某条候选消失了。

如果直接应用，系统可能执行一批与刚才预览载荷不一致的修改。

解法是让预览产出一个覆盖全部关键信息的摘要值：

```python
payload = json.dumps(
    [[i["ordinal"], i["memory_id"], i["content_sha256"], i["action"]] for i in items],
    sort_keys=True, separators=(",", ":"),
)
digest = hashlib.sha256(payload.encode("utf-8")).hexdigest()
```

注意它覆盖了**顺序**（`ordinal`）、**身份**（`memory_id`）、**内容版本**（`content_sha256`）和**动作**（`action`）四样东西。应用时重新算一遍再比对：

```python
if str(confirm_digest).strip() != digest:
    raise MemoryReviewError("confirmation digest does not match the previewed batch")
```

任何一条 ID、动作、内容或者顺序发生变化，摘要就对不上，应用被拒；应用阶段还必须重新核对当前队列和内容哈希。它能检测预览载荷与提交载荷的变化，降低陈旧提交风险。

这个摘要**不构成人工授权凭据**。摘要一致只能说明两份机器载荷一致，不能证明用户真的看过、理解了影响或有权批准。人工确认、身份校验和审计记录仍须由审核入口与组织流程承担。

当前界面还加了一道客户端保护：没有生成过预览就不允许点应用。它改善操作体验，但不能代替服务端校验。

### 一处实现与设计的偏差

原始设计是三段式：**先保存草稿 → 再预览影响 → 最后二次确认应用**，草稿要持久化。

实际实现里，「先保存」这一步**没有持久化** —— 当前审核前端把勾选结果放在界面的内存里，每次调用时把完整的决定数组同时传给预览和应用。台账里确实有一张草稿表，但那是早期一个已经退役的本地服务留下的，现行代码既不写也不读。

后果：审核到一半关掉界面，勾选丢失，得从头来。

这个偏差尚未修复。摘要校验降低了载荷漂移风险，但不能恢复关闭界面后丢失的选择，也不能证明人工授权。持久化草稿还会引入草稿失效与敏感数据留存问题，需要单独设计。**这是当前实现缺口，不是已经完成的设计。**

## 第四步：裁决写在独立覆盖层

应用成功后，写入四张表：

| 表 | 作用 |
|---|---|
| `lifecycle_overrides` | **覆盖层本体**，主键 `(memory_id, content_sha256)`，召回端唯一读的表 |
| `review_events` | 追加式事件流，记录「谁在哪个批次把什么从什么改成了什么」 |
| `batches` | 批次头，含预览摘要与状态 |
| `batch_items` | 批次明细，含备注、幂等键、错误码 |

六个动作到生命周期状态的映射：

```python
LIFECYCLE_BY_ACTION = {
    "keep_active":              "active",
    "review_later":             "review_required",
    "mark_legacy":              "legacy",
    "mark_expired":             "expired",
    "quarantine_wrong_subject": "quarantined",
    "supersede":                "superseded",
}
```

三个设计点：

**覆盖层是 UPSERT，事件流是追加。** 同一条记忆改判三次，覆盖层里只有最新一次，事件流里三次都在。想知道「这条为什么现在是过期状态」，查事件流。

**裁决流程不改写或删除原始向量记录。** 它读取原记录，并把判断写入独立台账。正常新增记忆以及经批准的替代流程仍会向记忆库插入新记录。

**`supersede` 被现行前端故意剔除。** 六个动作里只有五个开放。原因是替代操作会同时做两件事 —— 归档旧记忆、写入替代品 —— 而写入意味着这个审核工具需要具备记忆写入能力。这个能力目前保持关闭，因为一个「审核工具」拥有写入权限，本身就扩大了攻击面。需要替代时走正常的写入契约，而不是从审核界面里顺手做掉。

## 边界检查

审核入口做的几项防御，都很朴素但都有来历：

- **拒绝重复的记忆 ID**，防止同一批次里对一条记忆下两个矛盾的结论
- **拒绝不在当前队列里的 ID**，防止对着一份旧队列提交
- **拒绝内容哈希与队列不符的条目** —— 代码注释：审计哈希的是另一段文本，旧判断不能沿用
- **打开文件时用 `O_NOFOLLOW`**，拒绝符号链接，拒绝非普通文件，限制大小上限
- **所有读连接加 `PRAGMA query_only=ON` 和 `PRAGMA trusted_schema=OFF`**
- **单批次设有限上限**，具体数值属于实例配置
- 只读动作进白名单，`apply` 不在白名单里，走写路径的额外闸门

---

## 退休不等于删除

这套人工裁决流程里没有「删除」动作。

标为历史、过期、隔离，效果都是**退出自动召回**，记录本身还在。当前治理策略要求：可信异机备份和隔离恢复演练完成前，不通过自动清理或裁决路径删除记忆；健康报告中的 `deletion_allowed: false` 用来呈现这一状态。它是应用层约束，不是对同一账户下所有程序的操作系统级禁止。

理由不复杂：判断可能是错的。一条今天看着该退休的记忆，可能三个月后才发现当初判错了。留着，改判就行；删了，什么都没了。
