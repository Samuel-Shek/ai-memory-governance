# 06 · 健康备份与完整性

记忆系统有一个很讨厌的特性：**它坏掉的时候不报错**。

数据库连得上，检索有返回，AI 照常回答问题 —— 只是返回的记忆少了一半，或者多了一批本该退休的。你不会看到任何异常，直到某天发现 AI 的回答基于一个三个月前的事实。

所以健康检查的设计目标不是「服务是否可用」，而是「治理是否还在生效」。

---

## 六个维度

监督脚本定期跑，输出六个维度各自的状态，然后取最差的作为整体状态：

| 维度 | 检查什么 |
|---|---|
| `storage` | 加密卷挂载状态、容量水位、底层数据库快检 |
| `retrieval` | 语义检索是否还能捞到该捞的东西 |
| `quality` | 审计产物是否新鲜、积压是否失控 |
| `memory_scope` | 适用范围字段的合法性与覆盖率 |
| `backup` | 备份回执、恢复演练结果 |
| `access_control` | 各平台鉴权闸门、共享记忆策略、插件完整性 |

```python
overall = critical > attention/review_required > healthy
```

### 为什么必须分维度呈现

因为单一的「整体健康」指标很容易掩盖局部失效。

最典型的场景：数据库文件完好、能打开、能查询 —— 存储维度绿。但审核队列文件已经三天没更新了，质量维度其实该是黄的。如果只输出一个整体状态，存储的绿会把质量的黄冲掉，或者反过来，一个不重要的黄让人对整个报告脱敏。

所以有一条硬性规定：**底层数据库正常不能让整体自动显示「无问题」**。六个维度分开报，任何一个 critical 都决定整体是 critical。

### 实际是六维，规则文档写的是五维

早期设计里是五个维度，`memory_scope` 是后来加的 —— 因为适用范围这个字段在早期记忆里大面积缺失，需要一个独立的维度来跟踪补齐进度。

规则文档一直没同步更新，还写着五维。这是**文档与实现不一致的一个实例**，本篇按实现写。记在这里是因为它本身就是个教训：治理系统的文档腐化速度和代码一样快，而且更难被发现。

---

## 挂载状态：三种失效方式

加密卷这个设计（见 [01 · 存储层](01-存储层.md)）引入了一批新的失效模式，检查要能区分：

| 情况 | 含义 |
|---|---|
| `dangling_symlink` | 软链接在，指向的挂载点不存在 |
| `missing_path` | 软链接本身没了 |
| `volume_not_mounted` | 挂载点在，卷没挂上 |

这三种的处理完全不同，混为一谈会让排查绕远路。

更重要的是**卷没挂载时该怎么写健康报告**。

当前实例把完整健康报告写在受保护存储中。如果卷没挂载还硬写，文件可能落到内置盘上同名的空挂载点目录里 —— 于是出现两份治理状态：一份在卷里（旧的），一份在内置盘上（新的）。等卷挂回来，卷里的旧报告会遮住内置盘上的新报告，而你完全不知道发生了什么。

处理方式是**降级**：卷未挂载时只写一个私有状态文件，不碰公共报告。等卷回来了再正常写。

这类「状态分叉」问题在任何用可卸载存储的系统里都会出现，值得单独设计。

## 备份：验回执，不跑备份

健康检查的备份维度**不执行备份**，它检查最近一次备份留下的回执：

```
快照文件存在？
恢复演练结果 == "passed"？
底层库快检 == "ok"？
是否配置了可信的异机备份？
```

区分这两件事的理由：**跑过备份 ≠ 备份可用**。

一个每天忠实运行、每天产出一个损坏文件的备份任务，在「是否执行了备份」这个指标上永远是绿的。只有真的拿备份恢复一次，才知道它有没有用。

所以恢复演练是备份健康的必要条件，不是可选项。

这个维度的返回里有一个硬编码为假的字段：

```python
"deletion_allowed": False
```

它把 [04 · 生命周期与人工裁决](04-生命周期与人工裁决.md) 的治理状态显式写进报告：没有可信异机备份并通过隔离恢复演练前，自动清理和裁决流程不应删除记忆。这个字段约束遵守该策略的应用流程，不能阻止同一账户下的其它程序直接删除文件。

## 完整性：把配置钉死

最后一层，防的是**自己**。

几个月后为了排查某个问题，临时给某个客户端加一个环境变量扩大它的可见范围，改完忘了改回来 —— 这是这类系统最常见的腐化方式，而且几乎不可能被发现，因为它不产生任何错误。

对应的当前检查做两件事：

**一、用 SHA-256 核对核心文件。** 当前实例记录关键实现文件的内容哈希，对不上就翻红。公开文档不保留真实文件路径和具体文件清单。

**二、逐字段比对客户端配置。** 各 AI 客户端配置文件里登记的启动命令、参数、每一个环境变量，都跟期望值逐个比对。多一个、少一个、值不一样，都会让契约检查项翻红。

这一层的定位要说清楚：**它不防有同等本机权限的攻击者**。它主要发现无意腐化 —— 临时改动忘了恢复、复制粘贴带错值、升级时被覆盖。恶意维护者还可以同时修改文件和期望哈希。

## 通知：脱敏摘要，不发正文

治理状态变化时，会往一个即时通讯频道发一条摘要。这条通知的内容边界卡得很死：

**可以发**：内容大意、审核原因、不确定点、处理建议、审核前后对召回的影响。

**不能发**：记忆正文、完整的记忆 ID、发送者 ID、敏感来源信息、凭据、本机私密路径。

理由是即时通讯的内容不受控 —— 会同步到手机、会被截图、会留在服务器上。往那里发记忆正文，等于把加密卷的努力全部作废。

还有一条：**找不到精确的目标频道时只写本地状态，不回退到其它频道**。

这条来自一次真实的误投风险。通知逻辑最初写了个回退：找不到目标群就发到默认群。听起来很合理，直到你意识到「默认群」可能有别人在。宁可通知发不出去（本地留个状态，人自己会发现），也不能发错地方。

## 已知实现缺口

如实记两条，但不保留瞬时退出码、最近一次运行结果或精确调度频率：

**通知依赖调度执行。** 它不是持续受监督的常驻服务，因此「文档中存在通知设计」不能证明任意时刻的投递链路健康。当前状态必须在私有实例现场复验；公开仓库只保留这个架构缺口。

**六道召回过滤有三份独立实现。** 这一点在 [03 · 召回过滤](03-召回过滤.md) 末尾展开过。三份实现如果漂移了，没有任何自动化会发现 —— 这是当前设计里最实在的一个薄弱点。

把这两条写出来，是因为一份只讲设计有多完备、不讲哪里还没做到的治理文档，本身就不可信。
