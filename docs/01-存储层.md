# 01 · 存储层

## 三个决定

存储层只做了三个决定，但每个都影响到上层的全部设计。

### 决定一：整库放在加密卷上

当前实例把记忆库放在一个 macOS 加密稀疏磁盘映像（sparse bundle）里。下面只展示角色，不公开实例路径：

```
<memory-home>       →  软链接
<encrypted-volume> →  加密卷挂载点
<encrypted-image>  →  实体（APFS，加密）
```

卷密码存在系统钥匙串，由一个挂载脚本在开机时自动读取并挂载。对应地有一个卸载脚本 —— 卸载之后数据立刻回到加密状态，磁盘上只剩一坨读不懂的东西。

这么做的理由很直接：长期记忆库是所有 AI 数据里**信息密度最高**的一份。它是被反复提炼过的结论集，不是原始日志。一份跑了两年的记忆库，泄漏出去比泄漏两年的聊天记录更伤 —— 后者需要有人有耐心读完，前者是已经整理好的摘要。

用软链接而不是直接改配置路径，是为了让上层代码只认一个稳定入口，加密卷的存在对它们透明。代价是多了一个失效模式：卷没挂载时软链接会悬空，所以健康检查专门区分了「软链接悬空」「路径不存在」「卷未挂载」三种情况（见 [06 · 健康备份与完整性](06-健康备份与完整性.md)）。

### 决定二：嵌入和摘要走本地服务，受治理入口清理云端凭据

向量检索需要 embedding 模型，记忆提炼需要一个小 LLM。这两件事都在本地跑：

| 用途 | 选择 | 说明 |
|---|---|---|
| 向量库 | Chroma | 单 collection；元数据位于同一受保护存储中的 SQLite |
| 嵌入 | 本地 Ollama 模型 | 通过回环地址上的本地端点调用；模型名、端口和维度不公开 |
| 记忆提炼 LLM | 本地 Ollama 小模型 | 具体模型与参数属于实例配置 |
| 变更历史 | 独立 SQLite | 记录每条记忆的增删改 |

关键不在于「本地跑省钱」，而在于减少正文和凭据离开本机的路径。当前受治理入口在启动时主动清理已知的云端凭据、代理和 Python 环境变量：

```bash
unset OPENAI_API_KEY
unset ALL_PROXY all_proxy HTTP_PROXY http_proxy HTTPS_PROXY https_proxy no_proxy
unset PYTHONPATH PYTHONHOME VIRTUAL_ENV
```

清代理是因为本地服务不该走代理；清 Python 环境变量是因为这个脚本会被各种 AI 客户端从各种奇怪的环境里调起来，继承过去的 `PYTHONPATH` 会让它导入到错误的包（这类问题排查起来极其痛苦，因为报错发生在第一行 import，看起来像是脚本本身坏了）。

清 API key 这条最值得说：它的作用不是省钱，是堵住已知的云端降级路径。如果本地 Ollama 挂了，而环境里恰好有一个可用的云端 key，依赖库可能回退到云端。把受治理进程中的相关 key 清掉后，本地故障会显式暴露出来。这个动作只约束该进程继承的已知变量，不等于对所有网络或所有凭据来源做了操作系统级隔离。

### 决定三：裁决读原记录，判断写在别处

这一条严格来说是上层的设计，但它决定了存储层的访问模式，所以放在这里说。

当前人工裁决流程不对原始向量记录执行 `UPDATE` 或 `DELETE`。审核结论、生命周期状态、过期标记写在独立的 SQLite 覆盖层里；裁决读取向量库时使用只读连接。普通持久记忆写入和经批准的替代流程仍会新增记录：

```python
sqlite3.connect(f"file:{path}?mode=ro", uri=True)
# 读连接额外加：
#   PRAGMA query_only = ON
#   PRAGMA trusted_schema = OFF
```

好处是人工裁决本身不改写原记录，判断可以通过覆盖层重新裁定；坏处是召回时要多做一次本地联表查询。其它受治理的正常更新或替代路径仍可能新增或更新记忆，不能把“裁决只读”扩大解释为整个系统只读。

## 磁盘布局

```
<encrypted-volume>/
├── <vector-store>/
│   ├── <metadata-db>           向量库元数据（含记忆正文与 metadata）
│   └── <index-segments>/       向量索引分片
├── <history-db>                增删改历史
├── <backup-dir>/               本地备份
├── <governance-state>/
│   └── <health-report>         最近一次健康检查快照
└── <runtime-logs>/             运行日志（不应记录正文）
```

日志那一行的括号值得展开：当前日志策略只记录动作、结果类别、耗时和大小等运行信息，不应记录记忆正文。调试记忆系统时最容易犯的错，就是为了排查问题把请求响应整个打进日志 —— 然后得到一份没人治理的明文记忆副本。采用者仍需检查依赖库、崩溃报告和上层调用方是否另有日志，不能把这一条当成全进程证明。

## 参考改进建议：迁移要留回执

记忆系统的历史残留很难安全清理，因为旧目录可能仍是某些数据的唯一副本。采用者迁移向量库或目录时，应留下迁移回执：记录来源与目标的抽象标识、条目计数、校验结果、执行时间和回滚位置。删除旧副本前再做独立恢复验证。这个建议不代表当前实例已经自动化完成了残留清理。
