# 07 · 人类可读派生摘要

## 为什么需要这个东西

向量库里躺着几百条记忆，每条都有完整的元数据。这份数据对机器很友好，对人完全不友好 —— 你没法打开它看看「AI 现在到底认为我是个什么样的人」。

但这件事需要能看。理由有三个：

1. **记忆会跑偏，最终归属与有效性需要有人负责。** 自动检查可以发现部分异常，但 AI 从对话里误读出的「用户偏好 X」仍可能长期生效，直到经过可信来源核对和人工裁决。
2. **新会话的兜底。** 记忆工具不可用时（服务挂了、权限没通、在一台没配置的机器上），得有一个降级路径能让 AI 大致知道「机主是谁、有哪些长期约束」。
3. **交接和迁移。** 换机器、换客户端时，一份人类可读的摘要比一个二进制向量库好用得多。

所以有了一份派生摘要文件：一份 Markdown，几十行，按主题分节，写机主的长期偏好、规则入口、写入原则、稳定环境事实。

关键词是**派生**。它不是记忆的来源，是记忆的投影。改它不会影响向量库。

---

## 它不能自动发布

这是本篇唯一真正重要的设计决定。

自动生成一份摘要然后自动覆盖旧文件，技术上五分钟就能做完。但它有一个致命问题：**这份摘要会被 AI 当成事实读取**。如果生成逻辑出了偏差，或者源数据里混进了一条错误记忆，错误会在无人察觉的情况下变成 AI 眼中的「机主长期偏好」。

而且这种错误会自我强化 —— AI 基于错误的摘要行动，产生的新记忆又会带上这个偏差。

所以流程被拆成两半：**机器生成候选，人审核后原子发布**。

```
候选生成器（可以随便跑，跑一万次都无所谓）
   ↓  产出三份东西到一个候选目录
   ├── 候选文件           完整的新版摘要
   ├── diff               与当前已批准版本的逐行差异
   └── 证据 JSON          这次改了什么、依据是什么
   ↓
人看 diff 和证据
   ↓
原子发布（带候选文件的哈希）
```

---

## 候选生成器做什么

输入：当前已批准的摘要、核心规则文件、入口清单、最近的记忆质量报告和审核队列。

输出三份产物，写到一个专门的候选目录，全部用原子写入（同目录临时文件 + `os.replace`，权限 0600）。

生成器有一个关键的自我限制：**它只替换文件里的一段，不重写全文**。

```python
<!-- MEMORY_GOVERNANCE_STATUS:START -->
   ... 只有这一段会被自动替换 ...
<!-- MEMORY_GOVERNANCE_STATUS:END -->
```

标记之外的内容 —— 机主的长期偏好、写入原则那些人工维护的部分 —— 生成器一个字都不动。

这个限制很重要。一个能重写全文的生成器，一旦逻辑有 bug，会把人工积累了几个月的内容一次性冲掉。限定作用域之后，最坏情况是那一段治理状态写错了，其余部分完好。

### 证据文件

```json
{
  "generated_at":     "<ISO8601>",
  "change_scope":     "governance_status_block",
  "owner_id":         "<owner-id>",
  "from_token":       "<起始标记>",
  "to_token":         "<结束标记>",
  "replacement_count": 1,
  "approved_sha256":  "<当前已批准版本的哈希>",
  "candidate_sha256": "<候选版本的哈希>",
  "automatic_publish": false
}
```

当前候选生成器写出 `automatic_publish: false`，自身的直接发布子命令也会拒绝执行。字段让消费方能够校验生产方的能力声明，但字段本身不会阻止另一个程序覆盖目标文件；真正的发布边界仍在独立审核服务、哈希确认和文件权限中。

`approved_sha256` 和 `candidate_sha256` 这一对是发布时的防冲突凭据，下面说。

生成器自己在候选内容里写死了一句话：这一段只是自动生成的候选，只有机主检查过 diff 与证据之后，才能用带候选哈希的发布命令原子发布。

## 发布路径

生成器**自身的发布子命令已经被停用**，调用会直接抛出「直接发布已退役，请使用本地审核入口」。

发布迁到了审核服务里，逻辑是：

1. 比对候选文件现在的哈希，与请求里带的哈希是否一致
2. 不一致 → 抛出「候选在审核之后发生了变更」，中止
3. 一致 → 交给发布适配器执行，并校验回执
4. 发布记录写进台账的幂等表（候选哈希、证据哈希、回执哈希）

第 1、2 步和 [04 · 生命周期与人工裁决](04-生命周期与人工裁决.md) 里的预览摘要是同一个思路：**人审核的和系统执行的必须是同一份东西**。中间但凡候选被重新生成过，发布就得作废重来。

发布能力本身还有一个开关。如果配置的是一个「禁用发布」的适配器，这个能力就整个关闭 —— 用于那些只想要候选、不想要自动发布通道的部署。

## 三层记忆的分工

派生摘要是记忆体系里的第三层。三层职责必须分清，否则会出现互相覆盖的灾难：

| 层 | 是什么 | 权威性 |
|---|---|---|
| 共享向量库 | 跨 AI 的长期稳定结论主库 | **权威源** |
| 客户端原生记忆 | 某个 AI 客户端自己的证据索引与历史路由 | 局部索引，**不是主库的镜像** |
| 人类可读摘要 | 审核后发布的派生投影 | **只读参考**，不反向写回 |

三条红线：

- 客户端原生记忆**不作为主库的镜像**，也不反向全量覆盖主库
- 人类可读摘要**不得无人审核自动覆盖**
- 三者**不得盲目全量互拷或互相覆盖**

第三条来自实际维护经验：两层之间做双向同步，如果没有明确的冲突模型、权威顺序和回执，很容易产生静默覆盖。当前采用单向派生 —— 主库是源，其余是投影；投影不反向覆盖源，源变化后由投影重新生成并经人审核。

## 降级顺序

记忆工具不可用时，AI 该怎么办？有一个明确的顺序：

```
1. 当前环境提供的记忆工具
2. 受治理的命令行入口
3. 人类可读摘要 + 项目文件 + 现场证据
```

到第 3 层时有一条硬性要求：**必须明确说明缺口**。

不能假装记忆读到了。这一条属于诚实性要求，不是技术要求 —— 一个在记忆不可用时假装读到了记忆的 AI，比一个直说「我现在读不到长期记忆，以下回答只基于当前会话」的 AI 危险得多。
