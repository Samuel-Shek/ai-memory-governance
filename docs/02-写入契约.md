# 02 · 写入契约

写入是整套治理的第一道闸门，也是最重要的一道。一条记忆一旦带着错误的归属、伪造的审核状态或者过宽的适用范围进了库，后面所有的过滤都会老老实实地放它过去 —— 因为过滤器只认字段，不认字段是怎么来的。

## 裸文本写入是被禁的

最常见的记忆库用法是这样：

```python
memory.add("用户喜欢简洁的回答")
```

这行代码在当前受治理入口里会直接报错退出。原因是它什么都没说清楚：谁的偏好？什么时候观察到的？哪个平台适用？多久该复验？是稳定偏好还是这次对话的临时状态？

一条没有这些信息的记忆，进库之后就是一颗定时炸弹 —— 它永远不会过期，永远不知道该不该跨平台用，出问题时也追溯不到来源。

所以入口做了硬性拒绝：

```bash
if not isinstance(payload.get("metadata"), dict) or not payload.get("metadata"):
    print(json.dumps({"error": "structured metadata is required for durable writes"}))
    raise SystemExit(<non-zero>)
```

想写入长期记忆，必须提交结构化的载荷。这一条会让接入方觉得麻烦，但麻烦正是目的：**它让「随手记一条」这个动作变得有成本**，从而过滤掉大量本来就不该进长期库的东西。

## 受保护字段：服务端控制，不接受调用方覆盖

一条记忆的 metadata 分两部分：受保护字段和自由字段。

受保护字段一共 18 个，分四组：

| 组 | 字段 | 作用 |
|---|---|---|
| 归属 | `owner_id`、`memory_user_id` | 这条记忆属于谁 |
| 来源 | `source_system`、`source_platform`、`source_profile`、`agent_id`、`run_id`、`event` | 谁在什么运行环境下写的 |
| 时间 | `observed_at`、`written_at_utc`、`valid_until` | 什么时候观察到、写入、失效 |
| 生命周期 | `visibility`、`sensitivity`、`status`、`review_status`、`supersedes`、`applies_to`、`review_operation_key` | 可见性、敏感度、状态、审核结论、替代关系、适用范围 |

这 18 个名字都属于受保护集合。每次操作适用的字段由服务端生成，少数操作专用字段可以不存在。取值来自普通请求载荷不能直接覆盖的上下文：归属取自启动时校验过的 owner，时间取自服务器时钟，来源取自进程启动契约。能修改进程环境或服务代码的本地账户和管理员已经越过这条应用边界，见 [00 · 设计原则](00-设计原则.md) 的威胁模型。

然后 —— 这是关键的一行 —— 才合并调用方传来的 metadata，并显式丢弃其中所有同名键：

```python
base = _base_metadata(...)          # 服务端生成本次操作适用的受保护字段
base.update({
    k: v for k, v in _sanitize_metadata(metadata).items()
    if k not in RESERVED_METADATA_FIELDS          # ← 同名键直接被丢弃
})
```

### 丢弃与拒绝是不同取舍

当前适配器选择过滤调用方提交的受保护同名键，保留服务端值。另一种常见做法是只要调用方提交了这些键就拒绝请求。

两种做法都依赖所有写入路径一致覆盖。静默丢弃便于兼容旧调用方，但可能掩盖接入错误；显式拒绝更利于观测和纠错，但会提高迁移成本。**不存在“丢弃普遍比拒绝更安全”的结论。**

当前系统的多个适配器都各自执行了受保护字段过滤；这不是只有一行、天然不会漂移的实现。真正的验收标准应是：每一条普通写入和更新路径都不能让请求值成为受保护字段的权威值，并有测试覆盖这些路径。

更新已有记忆时，自由 metadata 里的受保护同名键同样会被过滤。适用范围若要变化，必须走显式的顶层参数并重新经过运行时范围授权；不能借自由 metadata 偷改。没有范围字段的遗留记录不能被静默提升为通用范围，应显式补齐或经管理流程处理。

## 内容闸门

字段说清楚了，内容本身还要过一遍检查。四种情况直接拒写：

**1. 空的，或者超长。** 当前入口设有正文长度上限，公开文档不保留实例数值。超过治理上限的东西通常更像「原文」而不是「结论」—— 原文该留在原处，长期记忆里应该放从原文提炼出的稳定要点。

**2. 原始会话片段。** 检查文本开头是不是各类客户端的会话前缀（形如 `[某平台 turn]`、`[某客户端] session=`）。这些是自动捕获逻辑漏出来的东西，属于典型的噪音污染 —— 一旦放进去，几个月后审计时会发现库里几十条这种，每条都要人工判断，非常消耗。

**3. 疑似密钥。** 正则匹配常见形态：

```
sk-[A-Za-z0-9]{20,}          常见 API key 前缀
Bearer\s+[A-Za-z0-9._-]{20,} 授权头
eyJ[A-Za-z0-9._-]{20,}       JWT
(?:password|api[_-]?key|secret|token)\s*[=:]\s*\S+
```

这个匹配肯定不完整 —— 世上的密钥格式太多了。它只能拦截一部分常见的误写形态，覆盖率没有在本仓库中量化，不能替代通用秘密扫描、最小权限和人工复核。

**4. 替代关系不能自己填。** `supersedes` 字段（声明「这条替代了旧的那条」）只能由服务端在专门的替代流程里设置，而且设置前要重新校验被替代的那条记忆内容没变过 —— 如果它变了，说明你要替代的已经不是你当初看到的那条了，流程中止。

## 独立校验器

私有系统有一个独立的契约校验工具：写入一条受控测试记忆，经检索路径读取，再直接检查底层数据库中的受保护字段。它用于验证「封装层声称写入」和「数据库实际落盘」是否一致。公开仓库不包含该工具，也不能复现这项实例验收。

这个工具存在的理由：契约代码本身可能有 bug，封装层可能在某次重构后悄悄漏掉了一个字段的写入。只看代码看不出来，只有直接查库才能确认「我以为写进去了」和「真的写进去了」是同一件事。

它和健康检查是两回事 —— 健康检查看的是系统当前状态，校验器验的是契约本身还成不成立。

## 完整性钉死

最后一层：当前实例有监督脚本用 SHA-256 核对写入链路的核心文件，同时逐字段比对各 AI 客户端配置中登记的启动命令、参数和环境变量是否等于期望值。

对纳入期望清单的文件和配置，内容或字段变化会让对应检查项翻红。它能发现已覆盖范围内的无意漂移，不能证明不存在漏列的文件、路径或恶意同步修改期望值的情况。

这一层防的不是外部攻击，是**自己**：几个月后为了排查某个问题临时改一行、改完忘了改回来，是这类系统最常见的腐化方式。
