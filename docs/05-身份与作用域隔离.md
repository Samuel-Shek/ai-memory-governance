# 05 · 身份与作用域隔离

两个独立的问题，经常被混为一谈：

- **身份**：这个请求是不是机主本人发起的？
- **作用域**：这条记忆该给哪个 AI 用？

在受治理服务路径里，第一个是访问控制问题，答错了会泄漏；第二个既影响质量，也可能影响隐私。两者都只是应用层边界，不能阻止拥有同等本地账户权限的进程直接访问存储。

---

## 身份：owner gate

### 谁需要被鉴权

本地 CLI、本地 MCP 进程没有远程「发送者」字段；当前设计把它们视为已经处在机主的本地账户边界内，并在启动时校验声明的 owner。不一致就退出。这个假设不防同一 macOS 用户下的恶意进程。

真正需要鉴权的是**网关**：AI 通过 IM 平台（群聊、私聊、机器人）接收消息时，消息可能来自任何人。这时候「谁在说话」变成一个必须回答的问题。

### 判定逻辑

```python
def _verify_owner(platform, user_id, user_id_alt=""):
    platform = str(platform or "").strip().lower()

    # 本地可信平台直通：CLI、桌面端、各 AI 客户端
    if platform in TRUSTED_LOCAL_PLATFORMS:
        return True

    candidates = {v for v in (user_id, user_id_alt) if v}

    # 内部身份：机主本人、定时任务、自动化
    if candidates & INTERNAL_OWNER_IDS:
        return True

    # IM 平台：查该平台各自的白名单环境变量
    allowed_ids = set()
    for env_name in PLATFORM_OWNER_ENV.get(platform, ()):
        allowed_ids.update(
            v.strip() for v in os.environ.get(env_name, "").split(",")
            if v.strip() and v.strip() != "*"      # ← 通配符被显式剔除
        )
    return bool(candidates & allowed_ids)
```

那个 `!= "*"` 是有来历的。IM 机器人的配置里经常有「允许所有人」这个开关，写法就是把白名单设成 `*`。如果授权逻辑接受该通配符，且没有其它有效闸门，未验证发送者就可能获得机主的长期记忆能力。

### 五道闸

未通过鉴权的发送者，在五个位置被挡住：

| 位置 | 行为 |
|---|---|
| 系统提示词 | 注入一句声明：本次会话共享记忆已禁用，只用当前会话上下文，不得声称或写入机主的长期记忆 |
| 预取 | 直接返回空字符串，不做任何自动召回 |
| 工具暴露 | 不向模型暴露记忆相关的工具 |
| 工具调用 | 返回错误：共享记忆对该发送者已禁用 |
| 子进程调用 | 当前网关插件的底层 CLI 路径再次校验，失败则抛异常 |

五道闸属于纵深防御，分别降低不同失效方式的影响：

- 第一道防的是**模型自己乱说**（「根据我记得的你的偏好……」其实什么都没读到）
- 第二、三道是正常路径的关闭
- 第四道防的是模型硬编造工具调用
- 第五道是更靠近底层调用的兜底，降低将来新增路径却忘记在入口加检查的风险

它们不能替代平台侧的真实 sender 鉴权，也不能证明不存在其它未纳入的调用路径。

### 拒绝事件只记哈希

鉴权失败要留审计记录，但审计记录里不能存原始的发送者 ID —— 那是第三方的个人信息，存下来本身就是隐私问题。

当前做法是只记 sha256 的短前缀，用于粗略关联重复拒绝事件。它减少了直接暴露原始 ID，但**不是匿名化**：如果候选 ID 空间很小或攻击者已经掌握候选值，仍可能被枚举比对。因此这类审计记录同样需要限权与留存策略。

### 平台侧闸门体检

监督脚本会定期读各平台的配置，检查这些条件：

- IM 平台的「允许所有人」开关必须是关闭
- 群聊策略必须是禁用
- 白名单必须非空
- 全局清单里的共享记忆策略必须是「仅限已验证机主」
- 插件源码里必须同时包含鉴权函数、验证标志、owner 常量三个标识

最后一条是防止有人（还是几个月后的自己）为了调试把鉴权整段注释掉之后忘了恢复。

## 作用域：共享服务入口，靠运行时配置约束

### 问题

三个 AI 客户端共用一个记忆库。有些记忆是通用的（机主的长期偏好），有些是平台专属的（某个客户端的特定用法）。怎么让每个客户端只看到该看的？

### 做法

多个客户端通过共享的服务入口和策略模块接入，运行时环境变量声明各自的读写范围。下例使用 `templates/runtime-scopes.example.env` 指定的 POSIX shell 赋值语法：

```sh
# 客户端 A
MEMORY_AGENT_ID="<client-a>"
MEMORY_SOURCE_SYSTEM="<client-a>"
MEMORY_DEFAULT_APPLIES_TO='["platform:<client-a>"]'
MEMORY_RUNTIME_SCOPES='["universal","platform:<client-a>"]'

# 客户端 B
MEMORY_AGENT_ID="<client-b>"
MEMORY_SOURCE_SYSTEM="<client-b>"
MEMORY_DEFAULT_APPLIES_TO='["platform:<client-b>"]'
MEMORY_RUNTIME_SCOPES='["universal","platform:<client-b>"]'
```

两个变量各管一头：

- `RUNTIME_SCOPES` 是**读侧白名单**。这个进程只能召回适用范围命中列表的记忆。客户端 A 看不到客户端 B 的专属记忆。
- `DEFAULT_APPLIES_TO` 是**写侧默认值**。写入时不指定范围，就被钉在本平台，不会意外变成通用。

写侧还有一层：调用方声明的平台、profile 或项目范围必须属于运行时允许集合，不能凭空发明其它范围。当前策略把 `universal` 作为显式允许的跨端目标，因此普通受信写入方可以主动选择它；环境变量中的平台默认值只能防止“省略范围时意外写成通用”，不能阻止写入方有意请求 `universal`。如果采用者需要更强隔离，应把跨端写入放到独立授权路径，这属于参考改进建议，不是当前实现。

### 合法的范围值

```
universal              跨全部 AI 共享
platform:<name>        某个 AI 客户端专属
profile:<name>         某个机器人配置/角色专属
project:<stable-id>    某个项目专属
```

封闭枚举。遇到不认识的值 —— **报错，而不是当成通用**。

这一条在代码里出现了两次（一次在范围规范化，一次在匹配判定），因为它太容易被写错了。「不知道该给谁看」的默认值应该是「谁都别看」，不是「谁都能看」。

### 这个设计的好处和代价

好处是多数范围差异可以通过启动配置表达，不必为每个客户端维护一套完整服务。共享策略模块也降低了裁决与 scope 判定的漂移。

代价是配置文件和环境变量成为**应用层治理边界**。谁能改它们，谁就能改变服务行为；它们不是 macOS 权限隔离。监督脚本逐字段比对客户端配置，是为了发现无意漂移，不是为了抵抗能够恶意修改本机文件的人。

另一个已知缺口是：基础召回过滤仍分散在三处适配实现。三端共享部分策略代码并不等于“不存在某个平台漏过滤的问题”；现场需要跨适配一致性测试才能降低这项风险。

## 三端接入的不对称

顺带记一个实践观察：三个 AI 客户端的接入深度不一样。

| 端 | 记忆接入 | 规则注入 |
|---|---|---|
| 客户端 A | MCP 登记 | 配置文件软链接，**无强校验** |
| 客户端 B | MCP 登记 | 配置文件软链接 + 适配层执行态 |
| 网关 | 原生插件 | 每轮请求前强制注入 + fail-closed 校验 |

网关那端因为是自建的，可以在每轮模型调用前插一个钩子，做到「规则块必须恰好出现一次，否则中止本轮请求」。两个商业客户端做不到这种强度 —— 它们只能通过配置文件加载规则，加载失败就是静默降级。

**这是当前接入条件下无法消除的不对称。** 如果设计依赖「规则一定被加载」，那么在商业客户端上这个假设不成立。关键的应用层强制逻辑必须落在实际执行的服务进程里，而不是只落在可能未加载的规则文本中。

这也是 [00 · 设计原则](00-设计原则.md) 第一条「信任的边界在进程里，不在提示词里」的实际由来。
