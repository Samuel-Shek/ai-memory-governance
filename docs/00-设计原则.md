# 00 · 设计原则

## 问题不在「能不能记」，在「记了之后怎么办」

给 AI 加长期记忆这件事，技术上早就不难了：一个向量库，一个嵌入模型，写进去，检索出来。市面上的记忆方案基本都停在这一步。

真正开始出问题，是在跑了几个月之后：

- 库里攒了几百条，其中相当一部分是几个月前的运行态事实 —— 那时候某个服务地址还没变，某个方案还没被推翻。它们**从来没有过期机制**，于是 AI 拿着一份几个月前的世界观在回答今天的问题。
- 同一件事有两条互相打架的记忆，一条说「用方案 A」，一条说「A 已废弃改用 B」。检索出来哪条排前面，取决于向量相似度，不取决于哪条是对的。
- 某次对话里出现了别人的简历、别人公司的资料，AI 顺手把它当成「用户的事实」写了进去。**主体归属错了**，而且没有任何人会发现。
- 一条记忆写进去时是给某个平台用的，结果所有平台都能召回它。
- 想清理，又不敢清理 —— 因为你不知道删掉的那条以后会不会有用，也没有一个安全的地方能先看看「删了会有什么影响」。

这些问题的共同点：**它们都不是检索质量问题，是治理问题**。再好的 embedding 也救不了一条内容本身已经过期的记忆。

这套系统的全部设计，都是围绕「一条记忆从写入到退休的整个生命周期该受什么约束」展开的。

本文把内容分成三种口径：**当前真实实现**指发布时已经核对过的现场行为；**已知实现缺口**指尚未解决的问题；**参考改进建议**只代表推荐方向。`templates/` 里的文件是示意参考，不能反过来证明私有系统已经实现了其中所有说明。

## 五条贯穿全局的原则

### 一、信任的边界在进程里，不在提示词里

规则文件、系统提示词、给模型的指令，全都是**软约束**。模型可能不遵守，可能被上下文里的内容带偏，可能在长对话里忘掉。把「不要写入密钥」写进提示词，跟真正拦住密钥写入，中间差着一整个执行层。

所以当前实现把关键约束尽量落在**服务代码里**，而不是只写在提示词里：
- 不许裸文本写入 → 入口脚本直接报错并以非零状态退出
- 不许伪造 owner → 服务端生成该字段，调用方传的同名值被**丢弃**
- 拦截常见疑似密钥 → 写入前匹配一组已知形态，命中就抛错；不把它当成完整秘密扫描

对已经落到服务端检查里的约束，模型不能只靠提示词绕过普通入口；但规则覆盖面仍取决于实现和测试。例如疑似密钥正则只能覆盖已知形态，不是完整的数据防泄漏系统。

### 二、受保护字段由服务端控制

这是本系统最核心的一个手法，值得单独说。

常规做法是「校验」：调用方传 `owner_id`，服务端检查它对不对，不对就拒绝。问题是校验逻辑一旦有疏漏，或者某个分支忘了校验，伪造就成立了。

这里的做法是：把 18 个字段名列入受保护集合（谁的、来自哪、什么时候观察到、生命周期状态、适用范围……）。每次操作所适用的字段由服务端根据受控启动上下文生成；少数操作专用字段可以不存在。之后才合并调用方传来的 metadata，并显式过滤其中所有受保护同名键。

```
base = 服务端生成的受保护字段
base.update({k: v for k, v in 调用方 metadata.items() if k not in 受保护字段})
```

在当前普通写入路径里，调用方没有覆盖这些字段的通道：同名值会被忽略。这里真正重要的是**服务端控制字段，并让所有写入路径一致执行**。静默丢弃并不普遍强于拒绝；拒绝更容易暴露调用方误用，丢弃则更利于兼容。采用者应根据可观察性和兼容性选择，但不能让调用方的值成为权威值。

### 三、fail-closed：拿不准就别给

自动召回链路上任何一处出问题 —— 审核队列文件不见了、格式版本对不上、owner 字段是空的、时间戳解析失败 —— 结果都是**返回空**，而不是「退回到上一个版本的名单」或者「先放行再说」。

这条原则有代价：偶尔会因为某个文件损坏而记忆整体失灵。但反过来的代价更大 —— 一次静默的放行，意味着已经判定该退休的记忆重新回到了 AI 的上下文里，而且没有任何人会注意到。

系统里有一处注释把这个取舍写得很直白：审核队列文件不存在时，**不能退回到旧版的名单**，因为旧版只标记「噪音」，不认识「冲突」和「过期」这两类候选，退回去等于让它们悄悄回到 prompt 里。

### 四、判断绑在内容上，不绑在 ID 上

人工审核一条记忆、判定「这条还有效，继续用」之后，这个判断存在哪？

如果按 `memory_id` 存，就出现一个漏洞：记忆内容被改了，ID 没变，旧的「继续用」判断还在生效 —— 你批准的是旧文本，放行的是新文本。

所以裁决记录的主键是 **(记忆 ID, 内容 sha256) 复合键**。内容一改，哈希变，查不到匹配的裁决，这条记忆自动回到「待审」状态，退出自动召回。

同样的思路也用在批次提交上：预览一批修改时会算出一个覆盖「顺序 + ID + 内容哈希 + 动作」的摘要值，提交时必须回传相同的摘要值，并重新核对当前队列和内容哈希。任何一项变化都会导致提交被拒。这个摘要只能检测预览载荷与提交载荷是否一致，**不能证明用户真的看过、理解或授权了这批操作**。

### 五、人工裁决不可省略，但要让人能看得下去

有些判断机器做不了：这条冲突里哪一条是对的？这条职业相关的记忆到底是不是机主本人的？这条运行态事实还准不准？

但「人工审核几百条记忆」这件事，如果做成「打开一个列表逐条读正文」，那它三天之内就会被放弃。

所以审核链路做了两件事来降低负担：

1. **审计产出的候选队列不携带记忆正文**，但仍包含 ID、内容哈希、分类、关系、时间和自由文本理由。这些 metadata 也可能敏感，仍需限制权限、同步和留存。
2. **正文按需单条揭示**，当前审核路径不把正文写入自己的持久化文件。批量操作主要围绕 ID、哈希和分类进行。

代价是审核时信息密度低，得多点几下。换来的是这套流程真的能持续跑下去。

## 一条记忆的完整生命

```
写入   →  受保护字段由服务端盖章，内容过闸门
存储   →  落在加密卷上的向量库，全本地嵌入，无云端凭据
召回   →  六道过滤 + 裁决叠加，任一不过就不进上下文
审计   →  周期性全库扫描，产出不含正文、但仍需保护的候选队列
裁决   →  预览影响 → 摘要确认 → 写入独立的生命周期覆盖层
退休   →  标为历史 / 过期 / 隔离，退出自动召回；原始记录不被删除
```

最后半句值得强调：**退休不等于删除**。裁决写在一个独立的覆盖层里；裁决流程不对原始向量记录执行 `UPDATE` 或 `DELETE`。正常新增记忆以及经批准的替代写入仍会向记忆库插入新记录。裁决判错后可以改判，历史事件流仍保留前后两次判断。

在没有配置可信的异机备份、并且做过隔离恢复演练之前，当前治理策略不允许自动清理和裁决流程删除记忆。健康报告里的 `deletion_allowed: false` 用来呈现这项应用层状态；它不能阻止同一账户下的其它程序直接删除文件。

## 威胁模型

### 重点防范

- 模型沿普通服务路径误操作；
- 调用方提交错误或伪造的受保护 metadata；
- 未验证的远程发送者召回或写入机主记忆；
- 过期、越界、待审或已被裁决阻断的内容进入自动召回；
- 启动配置、过滤逻辑和治理状态无意漂移。

### 明确不防范

- 同一 macOS 用户下的恶意进程绕过服务直接读库；
- 本机账号、已登录设备、操作系统或硬件失陷；
- 管理员或维护者恶意修改代码、配置、队列或台账；
- 具有等价本地权限的攻击者窃取解密后的数据。

运行时 scope 环境变量只是**应用层治理策略**，不是操作系统级安全隔离。它约束遵守服务入口的调用方；能改启动配置或直接访问存储的进程已经越过了这条边界。

### 脱敏边界

本文有意保留 Chroma、Ollama、SQLite、MCP 等公开技术名，也保留作者在 GitHub 和许可证中的公开身份。“脱敏”不等于匿名。真实路径、端口、模型维度、对象 ID、精确调度频率与即时运行状态统一改为占位符或概括描述；仓库不包含真实数据库、记忆正文、凭据或实例配置。

## 这套方案不适合谁

说清楚边界比夸大适用范围有用：

- **只有一个 AI、记忆条目在几十条以内** —— 治理开销远大于收益，直接用现成的记忆库就好。
- **记忆内容不涉及隐私、也不涉及会过期的事实** —— 比如纯粹的产品知识库，那更适合 RAG，不适合「记忆」这套东西。
- **需要多人共享同一份记忆** —— 这套系统的身份模型是单一机主（single owner），多用户场景下的权限模型完全不同，不能直接套。
- **希望全自动、不想人工介入** —— 做不到。这套设计的前提就是承认某些判断必须由人来做，它优化的是「让人做得动」，不是「让人不用做」。
