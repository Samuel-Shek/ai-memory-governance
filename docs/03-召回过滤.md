# 03 · 召回过滤

写入把住了「什么能进库」，召回把住的是「库里的东西什么时候能进 AI 的上下文」。

这两件事必须分开做。因为一条记忆的价值会随时间变化：写入时它是对的，三个月后它过期了；写入时它属于某个平台，后来那个平台的用法变了。如果只在写入时把关，库里就只会越来越多地积累「当时对、现在错」的东西。

## 六道过滤

当前普通召回路径会让每一条检索结果逐条过这六关。任何一关不过，结果不进入 AI 上下文。

```python
# ① 归属：三个归属字段必须一致，且等于当前 owner
owners = _result_owners(item)
if not owners or owners != {USER_ID}:
    return False

# ② 状态：只有 active 能出
if status != "active":
    return False

# ③ 审核结论：只有 approved 能出
if review != "approved":
    return False

# ④ 可见性：白名单枚举
if visibility not in {"private", "owner_only", "shared_safe"}:
    return False

# ⑤ 有效期：过期的出局，解析失败的也出局
if valid_until:
    try:
        expiry = datetime.fromisoformat(valid_until.replace("Z", "+00:00"))
        if expiry.tzinfo is None:
            expiry = expiry.replace(tzinfo=timezone.utc)
        if expiry <= datetime.now(timezone.utc):
            return False
    except ValueError:
        return False        # ← 注意这里

# ⑥ 适用范围：与当前运行时声明的范围求交集
return matches_runtime_scope(item, _runtime_scopes())
```

### 三个容易被写错的细节

**归属为空要判不通过。** 早期遗留的记忆可能没有归属字段。直觉上「没写归属」应该按「归属未知」处理，然后……然后就没有然后了，多数实现会放行。这里的写法是 `not owners` 直接返回 False —— **没有主人的记忆不给用**。这会让一批老记录退出自动召回，代价是要么补齐字段，要么让它们就此退休，两条路都比放行强。

**有效期解析失败要判不通过。** 上面那个 `except ValueError: return False` 很容易被写成 `pass`（解析失败就当没设置有效期）。但一个格式错误的有效期字段，最可能的成因是写入方在乱填 —— 这时候按「没有有效期」处理，等于给了一条永不过期的记忆。

**适用范围非法不能提升为通用。** 遇到一个不认识的范围值，处理方式是**报错**，不是当成「通用」。这一条在代码注释里被特意强调过：早期没有范围字段的历史记录，不提升为通用范围。原因很直白 —— 把「不知道该给谁看」解释成「谁都能看」，是这类系统最容易犯也最难发现的错。

## 第七道：人工裁决叠加

六道过滤只看记忆自身的字段。上面还叠了一层：人工审核的结论。

自动召回时，每条候选结果会去查一个独立的裁决覆盖层。逻辑是：

```
1. 整个策略处于 fail-closed 状态？        → 全部拒绝
2. 现场重算这条记忆正文的 sha256
3. 用 (记忆 ID, 现算的哈希) 去查裁决记录
4. 命中的生命周期在阻断名单里？          → 拒绝
   阻断名单 = 待审 / 需复核 / 稍后再看 / 历史 / 过期 / 隔离 / 已被替代
5. 命中且是「保持有效」？                → 放行
6. 在候选队列里但没查到匹配哈希？        → 拒绝（内容变过，必须重审）
7. 根本不在候选队列里？                  → 交回上面六道过滤的结果
```

第 6 步是这一层的核心价值，[00 · 设计原则](00-设计原则.md) 里已经说过：**批准绑在内容上，不绑在 ID 上**。

第 1 步的 fail-closed 触发条件包括：候选队列文件不存在、格式版本号不是当前版本、队列声明的 owner 与本机不符、条目结构非法、读裁决库时任何一个 SQLite 错误。任何一条命中，自动召回**整体返回空**。

队列文件不存在这一条特别值得说。直觉做法是「没有队列就当没有待审候选，全部放行」，或者「退回到上一个版本的队列」。代码里对此有明确的注释：不能退回旧版，因为旧版只标记「噪音」一类候选，不认识「冲突」和「过期」，退回去等于让这两类候选悄悄回到 AI 的上下文里，而且**没人会发现**。

## 手动检索不是审计旁路

系统提供两种检索模式：自动（AI 主动预取）和手动（人显式发起搜索）。

一个很自然的想法是：手动检索是人在操作，应该能看到全部内容吧？

不能。手动模式相比自动模式，唯一的区别是**额外补充了精确文本匹配的候选**（因为向量检索有时会漏掉字面命中）。但这些补充进来的候选，走的是**同一套**归属、生命周期、可见性、有效期和适用范围过滤。

代码注释里写得很清楚：手动检索可以补充精确文本命中，但它使用同一套过滤器，它**从来不是审计旁路**。

查看原始候选要走独立的显式审计模式。当前实现用一个管理模式环境变量区分该路径 —— 于是有了下面这个安排。

---

## 三处入口，同一个动作

审计模式的开关是一个环境变量。它的危险之处在于「继承」：如果某个 AI 客户端的进程环境里恰好有这个变量，它启动的记忆进程就会继承过去，于是这个客户端在毫不知情的情况下获得了绕过全部审核的能力。

所以三处入口在启动时做同一件事 —— 把它清掉：

| 入口 | 动作 |
|---|---|
| CLI 包装脚本 | `unset MEMORY_ADMIN_MODE` |
| MCP 服务进程 | 启动时 `os.environ.pop(...)` |
| 网关插件调起子进程 | 构造子进程环境时 `env.pop(...)` |

网关插件那处的代码注释把理由写得很直接：一个普通的模型进程，绝不该继承独立审核管理入口的旁路权限。

审核管理入口是另一个程序，由人工流程调用并显式设置该变量。这里的边界是**程序入口与操作流程不同**，不是环境变量自动证明“这是人”。能修改进程环境或直接调用管理程序的主体已经越过应用层治理边界。

---

## 共享策略模块，三处基础适配

六道基础过滤在三个接入适配中仍有各自实现（CLI 后端、MCP 服务、网关插件），裁决叠加和范围判定则共用一个只读策略模块。

这个安排是妥协的产物。理想情况下六道过滤也该抽到共享模块里，避免三份实现漂移。实际没做，因为三个进程的输入结构略有差异（比如 CLI 后端多一个 owner 形参）。

**这是当前实现的已知薄弱点**：共享模块降低了部分漂移，但不能消除三份基础适配不一致的风险。现场尚没有一项自动化验收能证明三处过滤永远等价。参考改进方向是把基础判断也收敛为共享纯函数，让三个进程只做输入结构适配，并增加跨适配一致性测试；这项改进尚未实现。

还有一处验证缺口：私有测试中的精确文本直接读取辅助逻辑没有完全被替身隔离。在带有现存本地库的普通运行环境里，某项检索测试可能把本地结果合并进测试夹具，导致失败输出和断言被污染。使用空存储运行器或显式注入直接读取适配器可以避免，但当前尚未修复。因此这里不以“私有测试全绿”作为公开实现的证明。
