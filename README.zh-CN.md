## 这解决什么问题

给 AI 加长期记忆不难：一个向量库、一个嵌入模型，写进去，检索出来。真正的问题出现在运行几个月之后：

- 过期的运行态事实没有退出机制；
- 互相矛盾的记忆按向量相似度竞争，而不是按事实正确性取舍；
- 第三方资料被误写成机主本人的事实；
- 某个平台专用的上下文被另一端召回；
- 想清理又不敢清理，因为缺少可预览、可改判的裁决路径。

这些不是检索质量问题，而是**治理问题**。再好的 embedding 也救不了一条内容本身已经过期的记忆。

## 当前真实实现的核心机制

| 机制 | 准确口径 |
|---|---|
| **受保护字段由服务端控制** | 当前适配器先生成归属、来源、生命周期和作用域字段，再过滤调用方提交的同名键。静默丢弃便于兼容，但并不普遍强于拒绝；拒绝在发现误用方面可能更好。关键是服务端控制，并覆盖全部写入路径。 |
| **裁决绑定内容版本** | 覆盖层主键是 `(记忆 ID, 内容 sha256)`。正文一改，旧裁决不再匹配，必须重新审核。 |
| **预览摘要检测载荷变化** | 摘要覆盖顺序、ID、内容哈希和动作；应用阶段还要重验当前队列与内容哈希。它检测的是预览与提交不一致，**不是**人工看过或授权过的凭据。 |
| **候选队列不存正文** | 队列仍包含 ID、哈希、关系、时间和自由文本理由，这些元数据也可能敏感，不能当作“无敏感内容”。 |
| **治理状态异常时 fail-closed** | 队列缺失、版本不符或结构非法时，自动召回不退回较旧、规则较少的名单。 |
| **共享策略降低漂移** | 作用域和裁决叠加共用策略模块，但基础召回过滤仍有三份适配实现，漂移风险没有消失。 |
| **退休与删除分离** | 裁决流程不对原向量记录执行 `UPDATE` / `DELETE`，结论写入独立覆盖层；正常新增记忆和经批准的替代写入仍会落库。 |

## 信任边界与威胁模型

这套机制重点防范：

- 模型通过普通服务路径误操作；
- 调用方提交错误或伪造的受保护 metadata；
- 未经验证的远程发送者读取或写入机主记忆；
- 过期、越界或已被裁决阻断的内容进入自动召回；
- 配置与治理规则无意漂移。

它不防范：

- 与记忆服务运行在同一 macOS 用户下的恶意进程直接读库；
- 本机账号被攻破；
- 管理员或维护者恶意修改代码、配置和台账；
- 已登录设备或操作系统失陷。

环境变量里的运行时 scope 是**应用层治理策略**，不是操作系统级安全隔离。能绕过服务直接读库，或能改启动配置的进程，不在这套机制的保护范围内。

## 脱敏边界

- GitHub 账号名、作者姓名和 MIT 许可证署名是有意公开的信息。
- “脱敏”不等于匿名。
- Chroma、Ollama、SQLite、MCP 等公开技术名保留，因为它们有架构说明价值。
- 真实路径、端口、模型维度、实时退出码、账号或对象 ID、精确调度频率等实例指纹，统一改成占位符或概括描述。
- 仓库不包含私有系统的真实源代码、数据库、记忆正文、凭据或实例配置。

发布前可以在本机使用私有禁词表，但公开仓库只保留通用秘密扫描，避免禁词表本身泄露私人标识。验收同时覆盖当前文件、Git 历史和从远端得到的新 clone。

历史重写也有边界：公开分支和新 clone 干净，不等于 GitHub 服务器已经清除孤立提交或缓存视图。GitHub 官方说明，涉及敏感数据时，重写历史后可能还需要联系 Support 才能完成服务端清理。参见 [从存储库中删除敏感数据](https://docs.github.com/zh/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)。

## 已知实现缺口

- 基础召回过滤仍有三份适配实现；共享策略模块只能降低、不能消除漂移。
- 审核勾选没有持久化为草稿，界面关闭后会丢失。
- 健康维度的历史文档曾落后于实现，旧材料可能仍保留旧口径。
- 通知依赖调度执行，不是持续受监督的常驻服务；当前运行状态必须回到实例现场核查。
- 私有召回测试有一处没有完全隔离本地存储：除非替换直接读取辅助逻辑或使用空存储运行器，否则可能混入本机结果。本仓库不声称私有测试套件全部通过。
- 五份示意模板只做了基础语法校验，未在另一台机器端到端部署验证。

## 适用与不适用

**适合**：多个 AI 客户端共用一份长期记忆；内容涉及隐私或会过期的事实；单一机主场景。

**不适合**：

- 只有一个 AI、记忆只有几十条；
- 纯知识库、内容不会过期；
- 多人共享同一份记忆库；
- 希望完全自动化、不接受人工复核。
